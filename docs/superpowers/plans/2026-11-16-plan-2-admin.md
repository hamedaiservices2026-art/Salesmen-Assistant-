# Plan 2: Admin Dashboard and Commission Editor — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A platform owner creates a company and its first admin; the admin manages users, company settings, target lines, monthly targets (form and Excel), coverage, focus items, mid-month incentives, policy documents and the monthly commission scheme (structured editor with live preview), and sees a team overview computed from the same engine as the rep screens.

**Architecture:** Same Next.js application. The admin lives under `/admin` (desktop web, its own sign-in with email and password); the rep app stays under `/app`. Business rules stay pure in `src/domain` (engine extensions, scheme validation, Excel row validation, team standing, policy sections). Every admin read and write is a `Ctx`-scoped function under `src/server/admin` that checks the caller's role on the server and filters by `ctx.companyId`; reading one rep's figures goes through `repCtx`, which hands the existing rep loaders a context for that rep after checking he belongs to the caller.

**Tech Stack:** as plan 1 (Node 22, pnpm, Next.js 16, TypeScript strict, Tailwind CSS 4, next-intl 4, Drizzle ORM 0.45 with drizzle-kit, PGlite, `postgres`, zod 4, Vitest 5, lucide-react), plus `exceljs` 4.4.0 for reading and writing `.xlsx`.

**Spec:** `docs/superpowers/specs/2026-11-14-salesman-assistant-design.md` (sections 5, 6, 7, 11), product truth in `PRODUCT.md` (including "Pilot commission rules"). Mockup for the admin overview: `docs/design/admin.mockup.html` (structure only; its navy, green and amber colours are superseded by `src/ui/tokens.css`). Inputs carried from plan 1: `.superpowers/sdd/2026-11-14-plan-1-rep-core/progress.md` and `final-fix-wave.md` ("Not in this wave").

**This is plan 2 of 4.** Not split: 22 tasks in 6 milestones. Milestones 1–3 (Tasks 1–13) are the owner's no-code path: at the end of Task 13 the owner can create a company, its admin, a rep, targets and a published November scheme entirely through the admin. Later plans: (3) AI day close, assistant reading the policy documents stored here, "what reps ask" on the overview; (4) push notifications and the admin's free-text notifications page, install guide, offline, the supervisor's mobile team view.

## Global Constraints

Copied verbatim from plan 1:

- All quantities are integers. Lines with unit `cases` store case counts. Lines with unit `value` store minor units (halalas; 100 per SAR). No floating-point money anywhere in `src/domain`.
- Currency default `SAR`; time zone default `Asia/Riyadh`; "today" is always computed in the company's time zone.
- Languages: `ar` (default, right-to-left), `en`, `ur` (right-to-left). Every user-visible string comes from `src/i18n/messages/*.json`; no hard-coded copy in components. Digits are always Western (`0-9`).

1. **A forged id from another company** (user, line, target, scheme, focus item, holiday, coverage update, policy, upload row login) posted to an admin or supervisor action: refused with `not_found`, nothing changes in either company. Tests in Tasks 7, 8, 9, 10, 11, 14, 15, 18, 19, 20.

3. **A published scheme that refers to a line later deactivated or a focus item later removed from the rep:** the rep's commission screen still renders (that component reports `no_target` or not met) and the editor flags the reference before the next publish. Test in Task 11.
4. **Two admins editing or publishing the same month's scheme at once:** the second save or publish gets `stale` and nothing is overwritten. Test in Task 11.
5. **A session of the wrong role** (admin session opening `/app`, rep session opening `/admin` or calling an admin action directly, supervisor acting on a rep who is not his) and **parallel password guessing**: redirected or refused; at most five password checks before the lock. Tests in Tasks 5, 6, 14.

**Interfaces:**
- Produces:

  - `attemptWithLockout(db: Db, userId: string, check: () => Promise<boolean>, now: Date): Promise<"ok" | "invalid" | "locked">` — the reservation discipline moved out of `signIn` unchanged in effect (one conditional UPDATE reserves a try and checks the lock; at most five checks run in parallel; a failure at the limit writes the lock; success clears only while unlocked), except that stale-counter recovery reads `failed_at` (set on each reservation) instead of `updated_at`, so admin edits to a user no longer delay recovery.
  - `signIn` (PIN) accepts only `rep` and `supervisor`; `signInWithPassword(db, email: string, password: string, now?: Date): Promise<SignInResult>` accepts only `admin` and `owner` (email trimmed and lowercased; same `invalid` for unknown email and wrong password, with the decoy hash).
  - `isStrongPassword(pw: string): boolean` — 10 to 128 characters with at least 5 distinct characters.
  - `hashSecret` writes `scrypt$16384$8$1$<salt>$<key>`; `verifySecret` accepts that and the plan-1 `salt:key` form.
  - `acceptAdminInvite(db, token, password, now?): Promise<{ ok: true; sessionToken: string; login: string } | { ok: false; error: "invalid" | "expired" | "used" | "weak_password" }>` — same claim-in-transaction discipline as `acceptInvite`, sets `password_hash`, voids other invites and sessions; refuses invites of `rep`/`supervisor` users as `invalid`. `acceptInvite` refuses `admin`/`owner` invites as `invalid`.
  - `requireRole(roles: readonly Role[]): Promise<Ctx>` — no session → `/signin` when `roles` includes `rep`, else `/admin/signin`; wrong role → `homeFor(ctx.role)`. `/app` layout uses `requireRole(["rep","supervisor"])`.
